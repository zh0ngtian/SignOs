# Cloudflare 软件源聚合与 IPA 元信息解析方案

状态：后端与客户端已实现，两个真实案例已验收；迁移按用户最新要求只保留各应用最新包，不导入原历史版本。生产发布以固定入口和发布凭证为准。更新日期：2026-10-11。

软件源配置、聚合、定时同步和元信息解析迁移到 Cloudflare，通过 SignOs 管理。IPA 保存在 GitHub Release 或用户填写的原始地址，用户直接从原站下载。自动解析失败时展示原因，不提供手动填写应用元信息的入口。

本方案记录软件源管理功能的设计目标。SignOs 客户端交付以项目 [AGENTS.md](../../AGENTS.md) 和 [GitHub Actions 构建检查](../../README.md#github-actions-构建检查)为准。

## 整体架构

| 组成 | 职责 |
| --- | --- |
| SignOs | 添加订阅、选择 IPA、修改匹配规则、查看同步结果 |
| Cloudflare Worker | 管理 API、Token 校验、公开软件源 JSON、HTTP Range 解析 |
| SQLite-backed Durable Object | 保存配置、应用元信息、版本记录、同步任务和已发布 JSON |
| Cloudflare Cron | 定期触发更新检查 |
| GitHub Release 或原始地址 | 保存 IPA，直接向用户提供下载 |

SQLite-backed Durable Object 支持免费计划，可作为配置和结果的持久存储。免费额度有请求、计算和存储限制；超额时操作可能失败，不能把免费计划理解为无使用上限。[Cloudflare Durable Objects 定价](https://developers.cloudflare.com/durable-objects/platform/pricing/)

远端保存软件源的权威数据，SignOs 本地保存缓存。重新安装 SignOs 后，添加同一个软件源地址即可恢复应用列表；配置编辑需要重新输入管理 Token。

Cloudflare 保存配置、JSON 和提取出的元信息，不保存完整 IPA，也不代理用户下载。部分解析仅临时读取必要片段，结束后不持久保留这些片段。本方案不需要 R2 或 Containers。

## 软件源和订阅项

软件源是对外提供的聚合列表；订阅项是一条获取某个应用更新的规则。一个软件源可以包含多个订阅项，同一个 GitHub 仓库也可以创建多个订阅项。

| 类型 | 用户填写 | 更新方式 |
| --- | --- | --- |
| GitHub Release | 仓库地址、Release 范围、IPA 附件匹配规则 | 定期检查符合条件的新 Release |
| 直接 IPA 地址 | 可直接下载的 HTTPS URL | 定期检查该地址对应的文件是否变化 |

订阅项可以跟踪不同应用，也可以分别跟踪同一应用的不同变体。订阅项使用稳定 ID，不能仅以仓库名或 Bundle ID 作为唯一标识。

## GitHub Release 添加与匹配

首次添加流程：

1. 用户输入 GitHub 仓库地址。
2. 默认选择正式 Release，可开启预发布版本，或限定 tag 前缀。
3. 列出目标 Release 中全部 `.ipa`，展示文件名和大小。
4. 只有一个符合条件的 IPA 时自动选择；有多个时由用户选择。
5. 自动解析选中的 IPA，展示应用名称、Bundle ID、版本等信息。
6. 用户确认后添加订阅，并保存附件匹配规则。

附件规则支持固定文件名和简单通配符，例如 `UTM-SE.ipa` 或 `Feather-*.ipa`。界面应展示规则及其当前匹配结果，允许用户调整。不能默认取第一个或最大的附件。

后续更新严格按规则处理：

| 匹配结果 | 行为 |
| --- | --- |
| 一个 IPA | 自动解析，通过校验后发布 |
| 没有 IPA | 展示“未找到符合规则的 IPA”，保留旧版本 |
| 多个 IPA | 展示候选文件，让用户重新选择或修改规则 |
| Bundle ID 与原应用不符 | 阻止自动更新，展示具体原因 |
| 解析失败 | 展示失败原因，保留旧版本 |

同一应用的不同变体即使 Bundle ID 相同，也分别保存订阅项和附件规则，避免混用。Release 的附件 ID 只用于记录当次候选，跨版本匹配依赖保存的规则。

普通仓库可以使用最新正式 Release；限定 tag 前缀、需要预发布版本或包含多个应用的仓库，应读取 Release 列表并分页筛选，不能统一依赖 `/releases/latest`。目标 Release 确定后，附件缺失或歧义应报错，不静默选择其他应用或旧 Release。[GitHub Release API](https://docs.github.com/en/rest/releases/releases)

## 直接 IPA 地址添加与更新

用户填写 URL 后，Cloudflare 自动进行 Range 解析。首次尾部请求从 `Content-Range` 获取文件总大小，不要求预先知道大小。

解析成功后预览并确认添加；失败时展示原因，提供“重试”和“修改下载地址”。

后续更新方式：

- 固定地址中的文件被替换：检测变化后重新解析。
- 每个版本都有独立地址：用户修改订阅地址后重新解析。
- 有可靠的 ETag 等变化标识时利用它判断变化；无法判断时按周期重新检查。

保存用户填写的原始地址。临时重定向产生的、可能过期的下载地址不写入公开软件源。GitHub 订阅保存对应 Release 的公开附件下载地址。

## IPA 元信息提取

采用 HTTP Range 部分解析：

1. 读取 IPA 末尾最多 65,557 字节，定位 ZIP 中央目录。
2. 中央目录不完整时补读需要的区段。
3. 定位主应用的 `Payload/<App>.app/Info.plist`，排除插件和扩展。
4. 读取对应 ZIP 本地文件头，确定压缩数据位置。
5. 只读取该 plist 的压缩数据，解压并校验长度与 ZIP CRC-32。
6. 解析 binary 或 XML plist，提取元信息。

65,557 字节覆盖常规 ZIP 结束记录及最大注释长度。ZIP64 应单独识别；不兼容时返回明确的格式错误，不能按常规 ZIP 偏移继续解析。

| 字段 | 用途 |
| --- | --- |
| 应用名称 | 软件源展示 |
| Bundle ID | 应用识别与更新校验 |
| 版本号 | 展示应用版本 |
| 构建号 | 区分同版本的不同构建 |
| 最低 iOS 版本 | 展示系统兼容要求 |

应用名称优先取 `CFBundleDisplayName`，其次取 `CFBundleName`。应用名称、Bundle ID 和版本号为发布所需信息，缺失时展示字段级错误；构建号和最低 iOS 版本缺失时留空，不推测值。

同时记录文件大小、原始下载地址、Release tag、附件名称和解析时间。应用元信息由解析结果产生，不提供手动填写或修改这些字段的入口。

每段读取校验 HTTP 206、`Content-Range`、实际响应长度及文件一致性；有强 ETag 时在后续片段读取中使用它。原站忽略 Range 返回完整文件时取消响应并报错，不自动退化为完整 IPA 下载。[HTTP Range 标准](https://www.rfc-editor.org/rfc/rfc9110.html#section-14)

CRC-32 校验的是提取出的 plist，不能代表完整 IPA 的 SHA-256。部分读取无法计算完整 IPA 的 SHA-256。

图标、截图等不是本次 Info.plist 提取的必备产物。迁移时保留已有展示资源；新应用先使用软件源默认图标，后续独立扩展图标提取。

## 同步任务与失败处理

默认每小时检查一次，SignOs 提供“立即同步”。

同步分为“检查更新”和“解析候选 IPA”两步。相同仓库的 Release 查询可以合并，每个 IPA 独立处理，避免在一次 Cron 调用里解析全部应用。任务状态持久保存，重试和重复触发不产生重复发布。

GitHub API 使用服务端 Token、条件请求和限流退避。新 Release 或附件发生变化时才触发解析，不在每次客户端刷新软件源时重复解析 IPA。[GitHub API 限流文档](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

| 场景 | 处理 |
| --- | --- |
| 新增订阅解析失败 | 保留失败记录供重试，不加入公开 JSON |
| 已有应用更新失败 | 保留上一次成功版本 |
| 网络超时、临时故障、限流 | 有限次数重试，显示下次重试时间 |
| 不支持 Range、格式不兼容 | 展示原因，等待修改地址或完善兼容性 |
| 多个主应用、解压或 CRC 校验失败 | 阻止发布，展示具体错误 |
| 多个附件匹配 | 等待用户选择或修改规则 |
| 读取期间文件变化 | 丢弃本次片段，重新解析 |
| 超过处理限额 | 展示限额原因，不覆盖已发布版本 |

一次更新全部校验成功后，才同时替换该应用的元信息和下载地址。批量同步中，一个应用失败不阻止其他应用更新。任务发布时核对当前订阅修订号，避免旧任务覆盖用户刚修改的规则。

失败页面展示用户可理解的原因及相应操作：重试、修改下载地址、重新选择附件或调整匹配规则。不展示手动填写元信息的表单。

## 远端数据与公开 JSON

| 数据 | 内容 |
| --- | --- |
| 软件源配置 | 名称、描述、稳定 ID、配置修订号 |
| 订阅配置 | GitHub 仓库或直接 URL、tag 规则、附件规则、预发布开关 |
| 应用与版本 | 提取的元信息、下载地址、上次成功版本、历史记录 |
| 同步状态 | 当前阶段、最近成功时间、失败原因、重试安排 |

公开入口形式：

```text
https://<软件源域名>/sources/<source-id>.json
```

JSON 按 SignOs 现有软件源格式输出，只包含已成功发布的应用数据。内部订阅配置和同步任务通过管理接口读取。

生成新 JSON 后原子替换已发布快照，并使用 ETag 和短期缓存。用户刷新软件源读取现成 JSON，不触发 IPA 解析。

提供配置及历史记录导出与恢复，导出内容不包含 Token。恢复时保留软件源身份和订阅项 ID。

## SignOs 管理功能与 Token

SignOs 增加软件源管理页面，支持：

- 添加 GitHub 订阅或直接 IPA 地址。
- 选择 Release 附件、修改匹配规则。
- 开关预发布版本、暂停或删除订阅。
- 查看解析与同步进度、失败原因。
- 重试失败任务、立即同步。
- 导出和恢复订阅配置。

公开 JSON 可直接读取；配置修改和主动同步操作需要管理 Token。Token 保存在设备钥匙串中，支持轮换和撤销。

软件源管理 Token 与 GitHub API Token 分开：前者用于 SignOs 管理软件源，后者仅存放在 Cloudflare 服务端，用于访问 GitHub API。公开 JSON 和导出文件都不包含这些凭据。

配置带修订号，多台设备同时编辑时检测冲突，避免覆盖其他设备的修改。

## 已验证范围

2026-10-11，正式部署的免费 Worker 在 HKG 节点完成以下实测：

| 样本 | IPA 大小 | 实际读取 | 耗时中位数 | 成功 |
| --- | --- | --- | --- | --- |
| Feather 2.9.0 | 14.24 MB | 66.0 KiB | 345 ms | 5/5 |
| UTM SE 4.7.5 | 213.88 MB | 139.5 KiB | 525 ms | 5/5 |

MB 为十进制单位，KiB 为 1,024 字节。耗时包含 Worker 等待上游下载及解析，排除本机调用 Worker 的网络耗时。上游均命中 GitHub CDN 缓存，结果不能直接推广为所有原站的下载速度。

UTM 的中央目录超出尾部读取范围，测试成功触发补读。两个样本均完成 plist 解压和 CRC-32 校验；五项元信息与完整下载后用 Python 提取的结果一致。

正式部署报告记录的三个 CPU 日志样本为 8、8、6 ms，未保存全部请求的 CPU 日志。免费 HTTP 请求 CPU 限额为 10 ms，完整业务加入后仍需重新验证 CPU 余量；不能仅凭这两种 IPA 保证所有文件均能处理。[Cloudflare Workers 限额](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)

已保存的验证资料：

- [免费 Worker Range 测试报告](evidence/free-worker-range-test-20261011.json)：10 次正式部署请求、Range 片段、耗时、元信息、CPU 样本和临时部署清理记录。
- [完整下载独立解析基准](evidence/ipa-full-download-baseline-20261011.json)：元信息、ZIP 路径、条目数、plist CRC-32 和全包 SHA-256 核验结果。

真实线上探针使用预先写定的文件大小，样本均为 binary plist。未知文件大小、真实 XML plist、ZIP64 和非 GitHub 原站仍需补测。当前结果验证了核心解析可行性，不代表管理 API、持久存储、调度、客户端或生产迁移已经完成。

## 实施顺序与验收

1. 完善解析器：补测未知文件大小、真实 XML plist、ZIP64、非 GitHub 原站及异常响应；校验失败原因与资源限额。
2. 完成 Cloudflare 后端：持久存储、Token、任务调度、失败状态、配置恢复和 JSON 原子发布。
3. 接入 SignOs 管理页面：完成添加、附件选择、规则编辑、冲突处理及失败展示。
4. 迁移现有软件源：每个应用只导入最新包和订阅配置，保留软件源身份、已有展示资源，以及 SignOs 自身的 Bundle ID 和升级身份；原历史包及凭证留在本机。
5. 核验新 JSON、原始下载链路和客户端更新后切换入口。旧客户端使用 `?legacy=1` 清单，只包含原有的默认变体；旧 HTTPS 入口重定向到该清单。新客户端在四个原有应用的默认变体都已公开且含全包散列后，才自动改写本地软件源 URL。

验收重点：

- 多 IPA 不误选，不同变体不混用。
- 解析失败展示原因，不要求手动填写元信息。
- 更新失败不覆盖已发布版本，单个订阅失败不影响其他订阅。
- 原始下载地址可用，用户下载直达 GitHub Release 或原站。
- 重新安装 SignOs 后可恢复列表；配置导出与恢复有效。
- 未授权写入被拒绝，Token 轮换与多设备编辑冲突正确处理。
- 完整流程在免费计划上通过实际 CPU、请求和存储额度验证。

实施按项目现有规则完成对应测试、提交、推送、必要服务部署和客户端流水线构建检查。实现与线上验收见下文；历史迁移完成后更新最终生产状态。
